# Исследование StoreMgr и эвристик сжатия памяти в Windows 11

## Введение

В современных версиях Windows (начиная с Windows 10 и развиваясь в Windows 11) традиционный механизм выгрузки страниц памяти (Pagefile) заменен гибридным подходом. Прежде чем записать данные на диск, ядро пытается сжать страницы (Memory Compression) и сохранить их в специальном пуле оперативной памяти — **Store**.

Этим процессом управляет компонент **StoreMgr** (`nt!Sm*` и `nt!SMKM_*`). Долгое время точные критерии (эвристики), по которым ядро решает, сжимать страницу или нет, оставались недокументированными.

## Архитектура StoreMgr

Исследование выявило сложную C++ структуру классов `SMKM_STORE` и `SMKM_STORE_MGR` внутри `ntkrnlmp.exe`.

### Ключевые компоненты:
1.  **Compress Manager (`SMKM_STORE_MGR::_SM_COMPRESS_MANAGER`)**: Главный координатор. Имеет выделенные потоки (Balancer Thread, Worker Threads), которые занимаются фоновым сжатием.
2.  **Compress Context (`_SM_COMPRESS_CONTEXT`)**: Хранит очереди страниц, ожидающих сжатия.
3.  **Memory Conditions**: Глобальное состояние системы, которое диктует агрессивность сжатия.

## Эвристики и условия памяти (Memory Conditions)

Анализ функции `nt!MiStoreUpdateMemoryConditions` раскрыл логику принятия решений:

1.  **Low IO Priority**: Перед началом активного вытеснения страниц, ядро проверяет, можно ли использовать `MiUseLowIoPriorityForModifiedPages`. Это означает, что если диск загружен (I/O давление), система предпочтет сжать память, а не писать в Pagefile, чтобы не усугублять ситуацию.
2.  **Available Pages Thresholds**: Оценивается количество доступных страниц. Функция `MiGetAvailablePagesBelowPriority` проверяет, достаточно ли свободной памяти.
3.  **Уровни Memory Condition (SMP_MEMORY_CONDITION)**: 
    *   При нормальной работе (много RAM) сжатие работает в "ленивом" фоновом режиме.
    *   Когда свободной памяти становится меньше определенных порогов (захардкоженных в ядре или вычисляемых динамически), приоритет потоков сжатия (`SmCompressCtxUpdatePriority`) увеличивается. В критической ситуации приоритет может быть поднят вплоть до уровня реального времени.

## Динамический приоритет потоков сжатия

Функция `nt!SMKM_STORE_MGR::SmCompressCtxUpdatePriority` динамически управляет важностью фонового сжатия:
*   Она вызывает `KeSetActualBasePriorityThread` для изменения базового приоритета потока сжатия.
*   Приоритет зависит от текущего `SMP_MEMORY_CONDITION`. На системах с архитектурой ARM64 (или гибридных x64) это также влияет на то, на каких ядрах (P-cores или E-cores) будет выполняться сжатие.
*   *Следствие:* Если ваша игра или тяжелое приложение резко начинает забирать память, Windows повысит приоритет потоков сжатия, что может вызвать внезапные всплески загрузки CPU (spikes), так как сжатие — ресурсоемкая операция.

## Алгоритм сжатия (LZ4)

Анализ функции `nt!SmStoreCompressBuffer` (которая является основной рабочей лошадкой для упаковки буферов) выявил прямой вызов алгоритма **LZ4**:

```asm
fffff800`6f55594c 97ff1195 bl  nt!LZ4_compress_fast_extState
```

В ранних версиях Windows использовались проприетарные алгоритмы семейства **XPRESS** (Xpress-Huffman, Xpress-LZ). Однако в современных сборках Windows 11 выбор сделан в пользу индустриального стандарта **LZ4**. 

**Причины перехода на LZ4:**
1. **Скорость декомпрессии (Декомпрессия важнее компрессии):** При сжатии RAM критически важно, чтобы при Page Fault (когда поток обращается к выгруженной странице) распаковка происходила мгновенно. LZ4 способен распаковывать данные со скоростью нескольких гигабайт в секунду на одно ядро процессора, что минимизирует задержки планировщика.
2. **Нулевая аллокация (extState):** Использование варианта `_extState` позволяет ядру переиспользовать заранее выделенные рабочие буферы (Workspaces) для каждого потока упаковщика, избегая дорогих вызовов `ExAllocatePool` в горячем пути.

## Работа со списками страниц

Анализ `nt!MiMoveModifiedPagesToCompressList` показал:
1.  Страницы забираются из **Modified List** (список измененных страниц).
2.  Ядро безопасно блокирует страницу (`MiSafeLockPage`).
3.  Страница отвязывается от обычных списков диспетчера памяти (`MiUnlinkPageFromListEx`).
4.  В структуру управления памятью записывается специальный флаг `MiSetStoreVirtualPagefileValue`, который указывает, что эта страница теперь "виртуально" в pagefile, хотя физически она уходит в компрессор.
5.  Страница ставится в очередь контекста сжатия `SmCompressCtxQueueEntries`.

## Интеграция с политиками питания (PPM)

Уникальная находка на ARM64 заключается в том, что `StoreMgr` активно консультируется с `nt!PpmPolicyConfigTable`. 
Например, функция `SmCompressManagerGetIdealProcessor` выбирает "идеальный" процессор для выполнения сжатия. В режимах экономии энергии (Battery Saver) фоновое сжатие может быть приостановлено или переведено строго на энергоэффективные ядра (E-cores), чтобы не разряжать батарею, даже если оперативной памяти не хватает.

## Вывод

Сжатие памяти в Windows 11 — это не просто алгоритм (хотя переход на **LZ4** подчеркивает фокус Microsoft на экстремальную скорость распаковки). Это комплексная экосистема, которая балансирует между I/O давлением на накопитель, доступной RAM, загрузкой CPU и политиками питания. Эвристика смещена в сторону предотвращения обращений к диску: система готова пожертвовать тактами CPU для сжатия данных, чтобы сохранить общую отзывчивость ОС (так как запись на SSD/HDD всегда медленнее распаковки из RAM через LZ4).
